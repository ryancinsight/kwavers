## KW-GPU-RUN-BUFFER-CAPACITY — A GPU PSTD run whose record buffer exceeds a device buffer limit panics [patch] — todo

priority: correctness; needs: none; basis: d1a3d463bfed5532f06d6ca5405ea64075335b27; scope: `crates/kwavers-gpu/src/pstd_gpu/time_loop/`, `crates/kwavers-gpu/src/pstd_gpu/pipeline/`, `crates/kwavers-gpu/src/pstd_gpu/runner.rs`, `crates/kwavers-simulation/src/runner.rs`, `docs/adr/037-gpu-pstd-output-contract.md`

- **Origin.** The second verdict on #1059 (comment 6815427401, finding 1). #1059 checks two construction buffers, `pml_xyz` and `shifts_all`; the buffers a run sizes are checked nowhere.
- **Read at the basis.** In `crates/kwavers-gpu/src/pstd_gpu/time_loop/buffer.rs`, `output_storage_lengths` (line 18) sizes the record at `n_sensors.max(1) * nt` values (line 24), plus one value per grid point when peak pressure is recorded. `build_run_cache` (line 80) creates `sensor_data` with that length (lines 108 and 109) and `sensor_indices`, `source_data`, `vel_x_data` and `sensor_staging` (lines 107 to 115); `ensure_field_staging_buffer` creates `final_field_staging` (line 76). Each goes through a `WgpuPstdBufferFactory` call that returns no error (`pipeline/buffers.rs`).
- **Run by the judge of #1059**, relayed from that verdict, on one host with an adapter, on an export of the second judged head of #1059 with a temporary test: `SimulationRunner::run` on a 16x16x16 grid with a full sensor mask, `time_steps` 8193 and the limits the provider requests panicked: "In Device::create_buffer, label = 'sensor_data' Buffer size 134234112 is greater than the maximum buffer size (134217728)". The judge reports `buffer.rs` unchanged between the basis and that head. Derived: 4096 sensors x 8193 steps x 4 bytes = 134234112.
- **Not run:** a request that exceeds a limit through `sensor_staging`, `final_field_staging`, `source_data` or `vel_x_data` alone. **Not known:** what a request returns when the device runs out of memory across buffers that each fit their limit (finding 5 of that verdict; a hypothesis until run on an adapter with less memory than the plan needs).
- **To carry** (the third verdict on #1059, comment 6816209700, findings 1 to 3; each read at the basis). `crates/kwavers-gpu/src/pstd_gpu/pipeline/mod.rs` line 7 says `with_auto_device()` "delegates to `new()`"; it calls `Self::construct` (`pipeline/auto_device.rs` line 60). `docs/adr/037-gpu-pstd-output-contract.md` line 71 names the unchecked buffers as those "a run sizes by sensors and steps"; `source_data`, `vel_x_data` and `final_field_staging` are sized otherwise. The `# Errors` lines of `run_gpu_pstd_with_provider` and `run_gpu_pstd_with_provider_outputs` (`crates/kwavers-gpu/src/pstd_gpu/runner.rs` lines 170 and 209) state the refusal for every provider; a provider that keeps the default `check_plan_capacity` refuses nothing.
- **Acceptance:** a run one of whose buffers exceeds a limit the device enables returns `KwaversError::ResourceLimitExceeded` naming the buffer, the bytes it needs and the limit, before the run creates a buffer, through `SimulationRunner::run`; no such request panics. A device test asserts the variant and the whole message for the request above, and the same grid with 8192 steps (134217728 bytes, the limit) runs. A check moved after the first run buffer fails a test, and the dispatch does not return a Leto result in its place. `pipeline/mod.rs` line 7, ADR 037 line 71 and `crates/kwavers-gpu/src/pstd_gpu/runner.rs` lines 170 and 209, which the bullet above names, say what holds after this change.
- **Next step:** list every buffer `build_run_cache` and `ensure_field_staging_buffer` create with its length; then check them where the run scalars and inputs are first known, before `build_run_cache`.
