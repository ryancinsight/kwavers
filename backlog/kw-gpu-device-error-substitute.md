## KW-GPU-DEVICE-ERROR-SUBSTITUTE — No test fails when a GPU PSTD request falls back to Leto on an error at or after device acquisition [patch] — todo

priority: verification; needs: none; basis: b3b2c3a372c8ceaf6f330637383e4d2cd11c43c4; scope: `crates/kwavers-simulation/src/dispatch/pstd/gpu.rs`, `crates/kwavers-simulation/src/solver_adapters/gpu_pstd.rs`, `crates/kwavers-simulation/src/runner.rs`

- **Origin.** Split from `KW-GPU-048`, which #1053 closes. ADR 037 says the runner "returns typed errors for unsupported inputs or acquisition failure". #1053 pins what the runner returns for two requests the provider refuses before device acquisition: zero time steps (`InvalidInput`) and two absorption exponents (`FeatureNotAvailable`). The Leto dispatch returns `Ok` for both (an empty record for zero steps). A fall-back fails a test only if it changes what one of those two requests returns. One that leaves both unchanged passes every test: for example one taken only for an error at or after device acquisition, or one that runs Leto and still returns the provider's error.
- **Read at the basis.** No test request reaches the errors at or after acquisition. The doc comment of `run_gpu_pstd` names `SystemError::GpuNotAvailable` (no adapter) and `KwaversError::GpuError` (an adapter that fails), and `with_auto_device` (`crates/kwavers-gpu/src/pstd_gpu/pipeline/auto_device.rs`) wraps a construction failure as `InvalidInput` ("GPU PSTD solver construction failed"). `git grep -n -i acquisition -- crates/kwavers-simulation/src` finds three doc comments, three test names and one `expect_err` message; no test makes acquisition fail. `run_gpu_pstd` fixes the device provider (`WgpuPstdStateProvider`); `run_gpu_pstd_with_provider` (`crates/kwavers-gpu/src/pstd_gpu/runner.rs`) takes it as a type parameter. No workflow runs the tests of the `gpu` build of `kwavers-simulation`.
- **Acceptance:** a test in which the provider returns an error at or after device acquisition for a `SolverType::PSTD` request with `FftBackend::Hephaestus`, on a request the Leto dispatch accepts, asserts that error's variant and message, runs where the gate runs, and fails when the dispatch or the adapter returns a Leto result instead.
- **Next step:** choose between a provider type parameter on the dispatch and the adapter, and a test for the adapter-less hosted runner; the second needs a workflow that runs the `gpu` build's tests (`KW-SIM-TEST-COMPILE-GRAPH`).
