## KW-GPU-DEVICE-ERROR-SUBSTITUTE — Every regression in which the GPU PSTD provider returns an error after device acquisition needs an adapter [patch] — todo

priority: verification; needs: none; basis: d1a3d463bfed5532f06d6ca5405ea64075335b27; scope: `crates/kwavers-simulation/src/dispatch/pstd/gpu.rs`, `crates/kwavers-simulation/src/solver_adapters/gpu_pstd.rs`, `crates/kwavers-simulation/src/runner.rs`

- **Origin.** Split from `KW-GPU-048`, which #1053 closes. ADR 037 says the runner "returns typed errors for unsupported inputs or acquisition failure". #1053 pins what the runner returns for two requests the provider refuses before device acquisition: zero time steps (`InvalidInput`) and two absorption exponents (`FeatureNotAvailable`). The Leto dispatch returns `Ok` for the two exponents; for zero time steps it returned an empty record until #1065, which makes it refuse them as `InvalidInput` with a message of its own. Run for #1053 as mutants of the dispatch, on a host with an adapter: a fall-back to Leto for every provider error, or for either of those two variants, failed a test, both when it returned Leto's outcome and when it kept the provider's error if Leto failed too. A fall-back taken only for `SystemError::GpuNotAvailable` or `KwaversError::GpuError` passed the 119 tests of the `gpu` build of `kwavers-simulation`, and so did one that runs Leto, drops its outcome and returns the provider's error. Run for #1065 on its integrator's development host, which has an adapter, at 5d9d0bc2a5e0fe55f3cb824b12fd037003918e5e: F', a fall-back to Leto for any `InvalidInput` at the `?` of `run_gpu_pstd` in `dispatch/pstd/gpu.rs`, or at the factory's Hephaestus arm in `solver_factory.rs`, that returns Leto's `Ok` and the provider's error when Leto fails too, passes the zero-step runner test and the zero-`dt` factory test, because Leto refuses both. It fails one test of the 126 of the `gpu` build at each site, `gpu_selection_reports_the_provider_source_rejection` and `reports_the_adapter_coefficient_rejection_for_hephaestus_pstd`, each a provider `InvalidInput` for a request Leto accepts. A fall-back for an `InvalidInput` whose message holds "time_steps" (the dispatch) or "dt" (the factory), keeping the provider's error, passes all 126; both paths refuse those requests, so it changes no outcome.
- **Read at the basis.** The doc comment of `run_gpu_pstd` names `SystemError::GpuNotAvailable` (no adapter) and `KwaversError::GpuError` (an adapter that fails), and `with_auto_device` (`crates/kwavers-gpu/src/pstd_gpu/pipeline/auto_device.rs` lines 60 to 65) wraps a construction failure as `InvalidInput` ("GPU PSTD solver construction failed"), except a capacity refusal, which it returns unwrapped. `git grep -n -i acquisition -- crates/kwavers-simulation/src` finds three doc comments, three test names and one `expect_err` message; no test makes acquisition fail. Where acquisition does fail, the run tests of `kwavers-gpu` discard the error: `make_solver` ends in `.ok()` (`crates/kwavers-gpu/src/pstd_gpu/tests/run.rs` line 45) and `test_gpu_pstd_run_produces_output` returns when it gets no solver (lines 59 to 61); the capacity device tests panic instead (`crates/kwavers-gpu/src/pstd_gpu/tests/capacity.rs` line 31); none of this was run on a host without an adapter. `run_gpu_pstd` fixes the device provider (`WgpuPstdStateProvider`); `run_gpu_pstd_with_provider` (`crates/kwavers-gpu/src/pstd_gpu/runner.rs`) takes it as a type parameter. No workflow runs the tests of the `gpu` build of `kwavers-simulation`.
- **Since #1059.** Three tests make the provider return `ResourceLimitExceeded` after it acquired a device, each ignored without an adapter: `a_limit_between_a_field_and_the_packed_pml_is_refused` and `a_limit_below_one_field_is_refused_before_any_buffer` (`crates/kwavers-gpu/src/pstd_gpu/tests/capacity.rs` lines 85 to 89 and 96 to 100), through `GpuPstdSolver::new`, and `gpu_selection_reports_a_plan_beyond_device_capacity` (`crates/kwavers-simulation/src/runner.rs`), through the dispatch, which gets the refusal unwrapped from `with_auto_device`. None of the three goes through the adapter of `solver_adapters/gpu_pstd.rs`. Four mutants of that change (an extra field buffer created inside the override, before the check; the refusal rewrapped as `InvalidInput`; the provider override removed; a Leto fall-back) fail only tests that need an adapter (its first verdict, comment 6814685775, finding 6). The Verification paragraph of `docs/adr/037-gpu-pstd-output-contract.md` records that none of the three goes through the adapter and that none makes the provider fail to acquire a device; the change that closes this item revises it.
- **Acceptance:** a test in which the provider returns an error at or after device acquisition for a `SolverType::PSTD` request with `FftBackend::Hephaestus`, on a request the Leto dispatch accepts, asserts that error's variant and message, runs where the gate runs, and fails when the dispatch or the adapter returns a Leto result instead.
- **Next step:** choose between a provider type parameter on the dispatch and the adapter, and a test for the adapter-less hosted runner; the second needs a workflow that runs the `gpu` build's tests (`KW-SIM-TEST-COMPILE-GRAPH`).
